1. Introducción

En el primer parcial diseñamos el sistema de reservas de una aerolínea regional y construimos su backend. En este segundo parcial el sistema tiene que funcionar de principio a fin y, además, tiene que poder medirse. La gerencia de la aerolínea quiere responder dos preguntas: ¿qué rutas llenan sus aviones? y ¿cómo le fue a una ruta concreta en un mes concreto? Para eso la aerolínea tiene dos años de historial de reservas, unos 2 millones de filas, que llegan como archivos CSV y están sucios: las rutas están escritas de varias maneras, los estados no son consistentes, hay filas repetidas y hay precios inválidos.

Nuestra solución tiene dos partes que no se mezclan. La primera es la parte que ven los clientes: una API y una página web donde se buscan vuelos y se reservan asientos, con una base de datos que garantiza que nunca se vendan más asientos de los que tiene un avión. La segunda es la parte analítica: un proceso por lotes limpia el historial con Apache Spark en Amazon EMR, guarda el resultado en S3 en formato Parquet, y el panel de la gerencia lo consulta con Amazon Athena. Todo lo desplegamos en AWS Academy Learner Lab, cuidando que la arquitectura fuera lo más simple y barata posible, porque el enunciado premia eso.

Este documento explica qué construimos, por qué tomamos cada decisión y qué evidencia tenemos de que funciona. Escribimos el texto pensando en alguien que no vio el desarrollo, y al final dejamos un glosario con los términos técnicos.

3. Vista general del sistema

La figura 1 muestra lo que realmente quedó desplegado. Lo importante es que hay dos caminos separados: el de las reservas y el del análisis.

N.ºElementoQué es
1ClientePersona que busca un vuelo y lo reserva desde el navegador, en la página principal (/).
2GerentePersona de la aerolínea que consulta la ocupación por ruta y mes en el panel (/manager): ve el porcentaje y el ranking de las 9 rutas.
3EC2 t3.smallMáquina virtual que ejecuta la API (FastAPI) y entrega el frontend React ya compilado. Es un solo proceso en el puerto 8000 y no necesita Node.
4RDS PostgreSQLBase de datos de vuelos y reservas. Es privada: solo la EC2 se conecta. Un UPDATE condicional impide vender un asiento de más.
5AthenaEjecuta SQL directamente sobre los archivos de S3, sin servidor propio. El panel le pregunta la ocupación; cobra solo por los datos que lee.
6Glue Data CatalogGuarda cómo son las 2 tablas (columnas y carpeta de S3) para que Athena las entienda. Con partition projection conoce los 24 meses sin crawlers.
7S3 curatedDatos ya limpios en Parquet, una carpeta por mes (month=2024-01...). Una consulta de un mes solo lee su carpeta, por eso escanea tan poco.
8EMR (Spark)Cluster temporal que lee los CSV, aplica las reglas de limpieza C1–C5 y escribe el Parquet. Se apaga solo al terminar, para no seguir cobrando.
9S3 rawEl historial tal como llega: 2 millones de reservas en CSV, con rutas mal escritas, estados raros, filas repetidas y precios inválidos.

El camino de las reservas

Un cliente abre la página, busca un vuelo y lo reserva. Esa petición llega a una máquina virtual EC2 que ejecuta un único proceso con la API (FastAPI) y que además entrega las páginas web (un frontend hecho con React, ya compilado). La API guarda y lee los datos en una base de datos PostgreSQL administrada por AWS (RDS). La base de datos no es pública: solo la EC2 puede conectarse a ella.

El camino del análisis

El historial crudo está en S3. Una vez, o cada vez que queramos actualizar el análisis, lanzamos un cluster de EMR que lee esos archivos, los limpia con Spark y escribe el resultado, ya limpio y en Parquet, de nuevo en S3. El cluster se apaga solo cuando termina. Glue guarda la descripción de las dos tablas resultantes (sus columnas y dónde están los archivos) y Athena usa esa descripción para responder consultas SQL directamente sobre los archivos de S3. Cuando la gerencia abre el panel, la API le pregunta a Athena y muestra el porcentaje de ocupación.

Los dos caminos solo se tocan en un punto: la API. Pero no comparten base de datos ni recursos de cómputo, así que analizar el historial nunca puede volver más lento el proceso de reservar.

4. Backend y frontend

4.1 La API

La API sigue exactamente el contrato del enunciado (apéndice A.1):

EndpointQué hace
POST /admin/flightsCrea un vuelo (id, ruta, fecha, capacidad y precio). Responde 201, o 409 si el id ya existe. La usa el harness para preparar vuelos de prueba
GET /flights/searchDevuelve los vuelos de una ruta y una fecha que todavía tienen asientos
POST /reservationsReserva un asiento. Responde 201 con el código de la reserva, 409 si el vuelo está lleno o 404 si no existe
GET /reservations/{id}Devuelve una reserva, o 404 si no existe
GET /analytics/occupancyDevuelve la ocupación de una ruta en un mes, calculada con Athena
GET /healthResponde 200 si la API está viva

4.2 La base de datos

Con este contrato solo hacen falta dos tablas. flights guarda cada vuelo con su capacidad y cuántos asientos lleva vendidos (seats_sold); reservations guarda cada reserva (id, vuelo, pasajero, clase y estado). En el primer parcial teníamos 19 tablas porque el sistema era más grande (tarifas, itinerarios con escalas, agencias, billetes). Aquí no se necesita ninguna de ellas, así que no las usamos: menos tablas significa menos consultas por petición, menos código que mantener y menos cosas que explicar. El esquema se crea solo al arrancar la API, sin herramientas de migración, porque con dos tablas no se justifica una.

4.3 Cómo evitamos vender un asiento de más (R2)

Este es el requisito que más puntos vale y el que más cuidado exige. El problema es el siguiente: si 50 personas reservan a la vez el último asiento, no podemos primero preguntar "¿queda cupo?" y después guardar la reserva, porque entre una cosa y la otra otro cliente puede haber tomado el asiento. Todos habrían visto "queda 1" y todos habrían reservado.

Lo resolvimos haciendo las dos cosas en una sola instrucción atómica de SQL:

UPDATE flights SET seats_sold = seats_sold + 1
WHERE flight_id = :id AND seats_sold < capacity

PostgreSQL bloquea la fila del vuelo mientras la modifica. Las demás peticiones esperan su turno y, cuando les toca, la condición seats_sold < capacity se vuelve a evaluar con el valor ya actualizado. Si la instrucción modificó una fila, había cupo y se guarda la reserva en la misma transacción (respuesta 201). Si modificó cero filas, ya no quedaba cupo (respuesta 409; o 404 si el vuelo no existe). Así, con 1 asiento y 50 clientes, exactamente uno gana y 49 reciben 409. Como segunda barrera, la tabla tiene una restricción CHECK (seats_sold <= capacity) que haría fallar a la base de datos si alguna vez algo intentara pasarse del límite.

Es el mismo bloqueo de filas que usamos en el primer parcial (SELECT ... FOR UPDATE), pero en un solo viaje a la base de datos en lugar de dos, lo que reduce la latencia cuando hay muchos clientes a la vez. Además dimensionamos el grupo de conexiones a la base de datos (20 permanentes y hasta 40 adicionales) para que 50 reservas simultáneas no se queden esperando una conexión.

4.4 El frontend

El frontend es una aplicación de una sola página hecha con React y Vite, con el mismo diseño que usamos en el primer parcial (barra azul con la marca RegionalAir, tarjetas, y modo oscuro automático). La compilamos a archivos estáticos y el mismo proceso de la API los entrega, de modo que el navegador siempre habla con un único servidor. Tiene dos pantallas:

  • Reservar (/). Se elige origen y destino (el campo sugiere los aeropuertos del historial), se escoge la fecha y se pulsa Buscar. Cada vuelo aparece con su ruta, los asientos disponibles y el precio. Al pulsar Reservar se piden el nombre del pasajero y la clase (económica o ejecutiva), y al confirmar se muestra una pantalla con el código de la reserva. Si el vuelo se llena mientras la persona decide, la página lo avisa con un mensaje claro en lugar de fallar.
  • Panel gerencial (/manager). Se escribe una ruta y un mes. Aparece una tarjeta grande con el porcentaje de ocupación, una barra de progreso, los asientos vendidos y la capacidad del mes. Debajo se muestra un ranking de las 9 rutas en ese mismo mes, ordenado de mayor a menor ocupación y con la ruta consultada resaltada. Eso responde la pregunta original de la gerencia ("¿qué rutas llenan sus aviones?"), no solo la de una ruta. La tarjeta aparece apenas llega su valor; las otras 8 rutas se piden en paralelo a Athena y se agregan después, y las rutas que no tienen datos en ese mes simplemente no aparecen.

Hicimos primero una versión muy simple, con HTML y JavaScript sin frameworks, que ya cumplía el contrato del harness. Después decidimos rehacerla en React retomando el diseño del parcial 1, porque se veía demasiado básica y porque queríamos que el panel contara mejor lo que mide el sistema. No reutilizamos las pantallas del parcial 1 tal cual, porque estaban hechas para otra API (búsqueda con pasajeros y escalas, tarifas, consulta por código de seis letras); reutilizamos su estilo y su estructura y reescribimos las páginas para el contrato actual. Los identificadores que exige el harness (data-testid) se conservaron en cada elemento.

Un detalle importante sobre la seguridad: el panel no pide usuario ni contraseña. No lo hicimos por descuido: el harness abre /manager y llama a /analytics/occupancy sin credenciales, y exigir un inicio de sesión haría fallar R7 y R9. Lo dejamos documentado como limitación (sección 11).

4.5 Cómo probamos antes de desplegar

Antes de subir nada a AWS corrimos el backend y las pruebas del harness en nuestro propio computador, con una PostgreSQL local. Ahí pasaron R1, R2, R3 y R8 (23 puntos). Eso nos permitió corregir errores sin gastar crédito del Lab.

5. El camino de los datos: de los CSV al panel

5.1 Los datos crudos

Con la semilla 963 generamos el historial con el programa que nos dio el profesor: 14.904 vuelos y 2.079.743 filas de reservas. Los subimos a un bucket de S3 (raw/). Los archivos son flights.csv (unos 430 KB) y reservations.csv (unos 81 MB). Están sucios a propósito, y por eso hay que limpiarlos antes de analizarlos.

5.2 Las cinco reglas de limpieza

ReglaQué haceEjemplo
C1En la ruta, quita todos los espacios y pasa a mayúsculas" bog - mde " se vuelve BOG-MDE
C2En el estado, quita espacios de los extremos y pasa a mayúsculas"confirmed " se vuelve CONFIRMED
C3Conserva solo los estados CONFIRMED y CANCELLEDUna fila con estado PENDING se descarta
C4Descarta las filas con precio vacío o menor o igual a ceroUn precio de 0, -500 o vacío se descarta
C5Si un reservation_id aparece más de una vez, deja solo la primeraLas copias exactas se eliminan

De las 2.079.743 filas crudas quedaron 2.009.247 filas limpias, es decir, se descartó un 3,4 % (70.496 filas: duplicados, estados desconocidos y precios inválidos). Ese número es exactamente el que el harness esperaba.

5.3 El trabajo de Spark en EMR

Spark es un motor que reparte un trabajo de datos entre varios procesadores para hacerlo en paralelo, y EMR es el servicio de AWS que levanta un grupo de máquinas ya configuradas con Spark. Nuestro programa (emr/job.py, en PySpark) hace lo siguiente:

  1. Lee los dos CSV desde S3. Todo llega como texto.
  2. Limpia los vuelos (C1) y las reservas (C2 a C5) con las reglas de la sección anterior.
  3. Une cada reserva limpia con su vuelo para saber su ruta y su mes (el mes es el de la fecha del vuelo).
  4. Escribe la tabla de detalle: una fila por reserva limpia, en Parquet, en carpetas por mes (month=2023-01/, month=2023-02/, ...). Son 24 carpetas con un archivo cada una.
  5. Calcula la tabla de métricas: para cada ruta y mes, la capacidad (suma de los asientos de todos sus vuelos, tengan o no reservas), los asientos vendidos (reservas CONFIRMED), los ingresos, las cancelaciones y la ocupación (vendidos dividido entre capacidad). Son 216 filas (9 rutas por 24 meses) en un solo archivo.

Una aclaración sobre la ocupación: las reservas canceladas no cuentan como asientos vendidos, solo las confirmadas. Y la capacidad cuenta los asientos de todos los vuelos del mes, no solo de los que vendieron algo.

Antes de usar EMR verificamos esta lógica con una muestra de 200 mil filas, primero en Spark local y luego en un cluster real de EMR. En las dos pruebas el resultado coincidió exactamente con el oráculo (la respuesta correcta que trae el harness): filas, ingresos por mes, capacidad, vendidos, cancelaciones y ocupación.

5.4 Por qué Parquet y por qué particionado por mes

Un CSV es texto: para leer una sola columna hay que leer todo el archivo. Parquet guarda los datos por columnas y comprimidos, así que una consulta solo lee las columnas que necesita, y los archivos pesan mucho menos (80,6 MB de CSV se vuelven unos 18 MB de Parquet en total). Además, al guardar cada mes en su propia carpeta, una consulta que pregunta por un mes solo abre esa carpeta y ignora las otras 23. En la prueba de R6, una consulta de un mes escaneó 295.129 bytes, mientras que el límite permitido era de 1.601.434. Sin Parquet y sin particiones, esa misma consulta habría tenido que leer todo el historial.

5.5 Glue y Athena

Los archivos Parquet por sí solos no saben cómo se llaman sus columnas ni dónde están. Glue Data Catalog guarda esa descripción: las dos tablas, reservations_curated y route_month_metrics, con las columnas exactas del contrato. Athena es un servicio que ejecuta SQL directamente sobre archivos de S3, sin servidor que administrar, y cobra solo por los datos que escanea.

Para que Athena conozca las 24 carpetas por mes sin tener que registrarlas una por una, usamos partition projection: en la definición de la tabla le decimos que el mes va desde 2023-01 hasta 2024-12 y que cada mes es una carpeta. Así no hace falta correr un rastreador (crawler) ni comandos de reparación, y las particiones quedan siempre al día.

5.6 El endpoint y el panel

Cuando alguien consulta /analytics/occupancy?route=SMR-BAQ&month=2024-01, la API lanza una consulta a Athena sobre la tabla route_month_metrics, espera el resultado y lo devuelve. El panel gerencial muestra ese valor como porcentaje con dos decimales. Como Athena no permite parámetros en este modo, la ruta y el mes se validan con un patrón estricto antes de entrar en la consulta, para que nadie pueda inyectar SQL. Si Athena tarda más de 9 segundos, la API responde con un error en lugar de dejar la página colgada.

6. Decisiones de arquitectura (sección 5 del enunciado)

Para cada decisión indicamos qué elegimos, por qué, qué alternativas descartamos, a qué requisito responde y qué pilar del AWS Well-Architected la respalda.

6.1 Dónde corre cada cosa

Elegimos una sola EC2 t3.small para la API y el frontend, y una RDS PostgreSQL db.t3.micro en una sola zona de disponibilidad y sin acceso público. Por qué: es lo más barato que cumple R1 y R2. R2 necesita bloqueo de filas, que PostgreSQL ofrece; y R1 se cumple con una máquina pequeña porque la búsqueda es una consulta con índice por ruta y fecha. Medimos un p95 de 0,228 segundos, muy por debajo del segundo permitido. Descartamos los contenedores con balanceador de carga (el balanceador cuesta unos 16 dólares al mes y no mejora ningún requisito), Aurora y DynamoDB (más caros, o sin el bloqueo de filas que necesitamos), y poner PostgreSQL dentro de la propia EC2 (ahorraría unos 14 dólares al mes, pero perdemos copias de seguridad administradas y aislamiento de los datos). Requisitos: R1, R2, R11. Pilares: Optimización de costos, Confiabilidad, Seguridad.

6.2 Por qué EMR y cómo nos aseguramos de que se apague

El curso exige usar EMR en este proyecto. Más allá de eso, tiene sentido: el historial viene sucio y hay que limpiarlo con reglas exactas, validarlo y agregarlo por ruta y mes. Athena sola podría escribir resultados con una consulta CTAS, pero tendríamos menos control sobre la transformación y escalaría peor si el historial se multiplicara. Un trabajo de AWS Glue sería equivalente, pero no es lo que pide el curso. Elegimos un cluster EMR clásico (versión 7.2.0) de un solo nodo m4.large, que es el único tipo disponible en el Lab; EMR Serverless no aplica.

Cómo evitamos que quede encendido (R10): lanzamos el cluster con la opción --auto-terminate. El cluster solo tiene un paso y, cuando termina, se apaga solo. Además, EMR no está dentro del stack de CloudFormation: así no puede quedar vivo por accidente ni cobrarse mientras dormimos. Lo medimos: una corrida dura unos 8 minutos en total (cerca de 6 minutos de arranque y 2 de trabajo), el harness contó 12 horas normalizadas contra un tope de 150, y al final no había clusters activos. Requisitos: R4, R10. Pilares: Optimización de costos, Sostenibilidad, Excelencia operativa.

6.3 Cómo organizamos los datos

Elegimos Parquet particionado por mes, con un archivo por partición, y la tabla de métricas en un solo archivo pequeño. Por qué: una consulta de un mes solo lee una de las 24 carpetas, y Parquet solo lee las columnas necesarias, así que Athena escanea una fracción del historial y cobra menos (295 KB en la prueba de R6). Requisitos: R5, R6. Pilares: Optimización de costos, Eficiencia de rendimiento, Sostenibilidad.

6.4 De dónde saca el panel sus números

El endpoint consulta Athena cada vez. Latencia: entre 1,5 y 2,5 segundos medidos, dentro del límite de 10 s. Costo por consulta: fracciones de centavo, porque cada una lee kilobytes y Athena cobra 5 dólares por terabyte escaneado. Frescura: los números son los de la última corrida de EMR; para un análisis gerencial, que mira meses completos, es suficiente. ¿Usamos caché? No lo justificamos: el volumen de consultas es bajo, el contrato exige que la primera petición de cada par consulte a Athena, y un caché solo valdría la pena con miles de consultas por día. Requisitos: R7, R9. Pilares: Eficiencia de rendimiento, Optimización de costos, Seguridad.

6.5 Cómo separamos las cargas de trabajo

Las reservas viven en RDS; el historial vive en S3 y se consulta con Athena, que es un servicio sin servidor; y el procesamiento pesado corre en EMR, fuera de la EC2. Por eso el análisis no consume conexiones ni procesador de la base de reservas. Dentro de la API, además, la reserva es una sola instrucción atómica y el grupo de conexiones está dimensionado para 50 clientes simultáneos. Requisitos: R1, R2. Pilares: Confiabilidad, Eficiencia de rendimiento.

7. Cómo desplegamos en AWS

El Learner Lab tiene restricciones que condicionaron el diseño: no se pueden crear roles de IAM, el bootstrap de CDK no funciona y los recursos viven solo mientras dura la sesión. Por eso la infraestructura está escrita con AWS CDK, pero la desplegamos generando la plantilla de CloudFormation y aplicándola con la CLI, usando los roles que el Lab ya trae (LabRole y LabInstanceProfile).

7.1 Los dos scripts

  • deploy.sh compila el frontend (React), empaqueta el backend y el frontend ya compilado, los sube a S3, crea una llave SSH y una contraseña aleatoria para la base de datos (que no se guarda en el repositorio), genera la plantilla con cdk synth y la aplica con aws cloudformation deploy. Crea la EC2, la RDS, el grupo de seguridad, la base de datos y las dos tablas de Glue, y el grupo de trabajo de Athena. Después espera a que la API responda. Tarda unos 10 minutos, casi todo por la RDS. deploy.sh destroy borra todo lo anterior y deja el bucket de datos.
  • run_emr.sh lanza el cluster de EMR, espera a que termine y muestra el resultado. Está separado del despliegue a propósito, por lo explicado en la sección 6.2.

7.3 Orden en que lo ejecutamos

  1. Generamos los 2 millones de filas con la semilla 963 y los subimos a S3.
  2. Ejecutamos deploy.sh y run_emr.sh a la vez, en dos terminales.
  3. Cuando la API respondió y EMR terminó, ejecutamos el harness completo contra la URL de la EC2.
  4. Al terminar la sesión ejecutamos deploy.sh destroy y comprobamos que no quedara nada encendido (ni EC2, ni RDS, ni NAT, ni clusters de EMR).

8. Proyección de costos

Supuestos. Imaginamos un uso gerencial normal: unos 50 usuarios internos, unas 2.000 búsquedas y 200 reservas al día, unas 100 consultas a Athena al día, y una corrida mensual de EMR de media hora con un nodo m4.large. El historial pesa unos 100 MB en CSV y unos 20 MB en Parquet.

El harness estimó 27,95 dólares a partir de lo que realmente estaba desplegado. La diferencia de unos 3,9 dólares se debe a que su estimación no incluye el almacenamiento (EBS y el disco de la RDS); queda dentro de la tolerancia y, en ambos casos, muy por debajo del tope de 50 dólares del Lab. Eso sí, solo es cierto si destruimos el stack al terminar cada sesión.

¿Qué pasa con el costo si el volumen de datos o de consultas se multiplica por 10? No se multiplica por 10. La EC2 y la RDS, que son cerca del 90 % del total, son costos fijos: no crecen porque haya más historial. Con diez veces más datos, S3 pasaría de unos 0,10 a unos 1 dólar y EMR de 0,20 a entre 1 y 2 dólares (más nodos o más tiempo, una vez al mes). Con diez veces más consultas, Athena pasaría de 0,10 a unos 1 dólar, porque cada consulta sigue leyendo una sola partición. El total subiría de unos 32 a unos 36 dólares, alrededor de un 12 %. Esto se debe a dos decisiones: Parquet con particiones (menos bytes escaneados, que es optimización de costos) y no tener cómputo analítico encendido todo el tiempo (sostenibilidad: consumimos energía solo mientras corre el trabajo).

10. Problemas que encontramos y cómo los resolvimos

  1. Una inconsistencia en la columna bookings. El enunciado y el contrato de datos dicen que bookings cuenta solo las reservas CONFIRMED. Pero el oráculo del harness (oracle.route_month_metrics) la calcula sobre todas las reservas válidas, confirmadas y canceladas. Ninguna prueba compara esa columna con el oráculo (solo revisa que exista), así que no afecta la nota. Seguimos lo que dice el contrato escrito (bookings = seats_sold) y lo dejamos documentado.
  2. El primer intento de EMR se atascó por falta de memoria. Con la configuración por defecto de Spark en un solo nodo m4.large, el proceso principal (driver) ocupó casi toda la memoria disponible y los procesos que hacen el trabajo (ejecutores) nunca llegaron a arrancar. Después de 12 minutos con un solo contenedor lo cancelamos a mano. La solución fue fijar la memoria de forma explícita (1 GB para el driver, 3 GB y 2 núcleos para el ejecutor, sin asignación dinámica). Con eso el trabajo tarda unos 2 minutos.
  3. El primer despliegue se revirtió por un carácter inválido. CloudFormation rechazó la descripción de una regla del grupo de seguridad porque contenía el carácter >, que AWS no admite. El despliegue se deshizo antes de crear la base de datos, así que no costó nada; cambiamos el texto y el segundo intento funcionó.
  4. Spark en Windows. Spark necesita un programa auxiliar de terceros (winutils.exe) para escribir archivos locales en Windows, y preferimos no instalarlo. Por eso, en local verificamos la lógica de limpieza en memoria contra el oráculo, y la lectura y escritura en S3 la validamos directamente en EMR.
  5. El frontend no mostraba vuelos al principio. Al abrir la página la primera vez, la búsqueda decía que no había vuelos con cupo. No era un error: la base de reservas estaba vacía porque el historial de 2 millones de filas vive en S3, no en la base transaccional. Escribimos un script (tools/crear_vuelos.py) que crea vuelos de demostración a través de la API.

11. Limitaciones que aceptamos

  • La API no tiene autenticación. POST /admin/flights está abierto porque el contrato del parcial lo exige para que el harness pueda crear vuelos de prueba. En un sistema real lo protegeríamos con red privada, una clave o un rol.
  • El tráfico va en HTTP, sin cifrado. Dejamos el puerto 8000 abierto para que el profesor pueda calificar. Agregar HTTPS exigiría un balanceador o un proxy, con costo y complejidad que R11 desaconseja.
  • La contraseña de la base de datos aparece en la plantilla de CloudFormation. La herramienta lo advierte. La genera al azar el script de despliegue, no se sube al repositorio, y la RDS no es pública: solo acepta conexiones desde el grupo de seguridad de la EC2.
  • Una sola zona de disponibilidad. Si esa zona falla, el sistema cae. Es una decisión consciente por costo: R11 prohíbe Multi-AZ.
  • El panel no es en tiempo real. Muestra los datos de la última corrida de EMR.
  • La demo depende de que el Lab esté encendido. El sistema solo está en línea mientras el stack esté desplegado, y la dirección IP de la EC2 cambia en cada despliegue.
